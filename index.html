01 • Introduction

01System Overview

What is QUEUESKI?

QUEUESKI is a student portal and queue-management system designed to organize student service requests, accounting transactions, document requests, and office queues.

Primary goals

  • Organize student requests and office services.
  • Manage queue tickets and their current status.
  • Maintain student account and transaction information.
  • Allow students to request Registrar documents.
  • Support payment submission and administrative verification.
  • Provide staff with tools to handle requests and queues.

👨‍🎓 Student

Uses the portal to access student-facing services, submit applicable requests, and view request or queue information.

🧑‍💼 Admin

Handles assigned office operations, queue management, and administrative tasks permitted by the system.

💰 Accounting

Handles student charges, payments, and payment-review-related operations.

📋 Registrar

Handles document requests and their processing statuses.

Implementation note This guide documents the known project structure. A feature described here should not be assumed fully operational until it has been tested.

03 • Features

03System Modules

Admin Dashboard

  • Displays administrative dashboard information.
  • Supports queue and assigned-office operations.
  • Uses backend endpoints to retrieve and update records.

Student Accounts

  • Provides student-related account information.
  • Uses student records and associated enrollment information.
  • Requires appropriate authentication and authorization.

Queue Management

  • Creates and manages office queue tickets.
  • Associates a queue ticket with a student and request.
  • Tracks waiting, preparing, serving, completed, or cancelled states.
  • Supports administrative queue actions and counter assignment where applicable.

Accounting

  • Records student charges and payments.
  • Uses accounting transactions as the financial ledger.
  • Supports payment submissions and administrative review.
  • Connects payments to applicable charges through bill allocations.

  • Loads available document types from the database.
  • Allows multiple document types in one request.
  • Supports quantities from 1 to 5 for each selected type.
  • Calculates document subtotals and the combined total.
  • Creates one parent request, individual item records, and one queue ticket.
  • Creates separate accounting charges for each document item.

Settings and appearance

  • Supports theme selection where implemented.
  • Uses JavaScript and browser storage for applicable interface preferences.
  • Includes administrative settings and navigation features in the portal.

05Database Tables

The project database is named queueski_db. The following tables are part of the documented structure; confirm column names, data types, foreign keys, and constraints in your actual schema.

TablePurposeKey relationship

Document catalog: document_types

Important fields include:

  • id — primary key.
  • document_name — unique document name.
  • fee — configured fee for one unit.
  • is_active — whether the document is offered.
  • created_at and updated_at — timestamps.

Document items: registrar_request_items

Important fields include:

  • request_id — parent request identifier.
  • document_type_id — selected catalog entry.
  • document_name — stored document-name snapshot.
  • quantity — number of copies requested.
  • unit_fee and total_fee — item pricing.
  • charge_transaction_id — related accounting charge.
  • status — current state of the individual item.
Why keep a fee snapshot? Saving unit_fee and total_fee on each item preserves the price used when that request was submitted, even if the catalog fee changes later.
06 • Registrar

06Multi-Document Workflow

How one request works

  1. The frontend loads active document types from api/document_types.php.
  2. The student selects one or more document types.
  3. The student chooses a quantity from 1 to 5 for each selected type.
  4. The interface displays each subtotal and the combined total.
  5. The student provides the request purpose and submits the form.
  6. The backend validates the selection and recalculates the fees.
  7. One parent record is inserted into registrar_requests.
  8. One item record is inserted for each selected document type.
  9. A separate Accounting charge is created for each item.
  10. One queue ticket is associated with the parent request.
  11. Payment must be verified before the request is allowed to enter processing.

07 • Accounting

07Payment Verification

Payment-review process

  1. The student submits payment information or a receipt.
  2. The submission is stored with a review status.
  3. An authorized administrator opens the payment-review interface.
  4. The backend checks the submission and its saved bill allocations.
  5. The allocations must refer to charges belonging to the same student.
  6. The allocated amount must match the submitted payment amount.
  7. The backend checks the charges and existing allocations to prevent overpayment.
  8. When valid, a payment transaction is recorded and the submission is marked verified.
  9. The related Registrar item statuses are updated where applicable.

Important validation checks

  • Confirm the administrator is authorized to review payments.
  • Use database transactions to keep related changes consistent.
  • Lock relevant records during verification where needed.
  • Reject invalid or mismatched bill allocations.
  • Prevent a bill from being paid beyond its remaining balance.
  • Do not mark Registrar items as paid when their charges were not included in the verified allocation.
Current integration reminder The documented payment-review fix updates linked Registrar items from awaiting_payment to payment_verified when their allocated charges are verified. The Admin queue endpoint still needs a tested payment-status gate before unpaid requests can be processed.

08Queue Management

Queue ticket information

The documented queue_tickets table includes:

  • student_id — student associated with the ticket.
  • request_id — associated request, with a unique constraint.
  • office — Accounting or Registrar.
  • queue_number — ticket number.
  • school_year and term — academic context.
  • status — ticket's current state.
  • assigned_admin_id and counter_number — assignment information.

Registrar processing gate A ticket's existence does not prove that payment has been verified. Before an Admin starts processing a Registrar request, the backend should confirm that every required item has an eligible payment status. This check must run server-side, not only in the interface.

10 • Learning Reference

10Programming Concepts

Prepared statements
Prepared statements separate SQL structure from supplied values. They help prevent SQL injection when used correctly.
PHP · PDO 
$stmt = $pdo->prepare(
    "SELECT * FROM students WHERE Student_ID = ?"
);

$stmt->execute([$studentId]);

$student = $stmt->fetch(PDO::FETCH_ASSOC);
Database transactions
A transaction groups related database operations so they can be committed together or rolled back if an operation fails.
PHP · PDO 
try {
    $pdo->beginTransaction();

    // Perform related database changes.

    $pdo->commit();
} catch (Throwable $e) {
    if ($pdo->inTransaction()) {
        $pdo->rollBack();
    }

    throw $e;
}

Example pattern only. Production code should log exceptions and return safe error messages rather than exposing internal details.

Sessions and authorization

PHP sessions maintain information associated with a logged-in user. Authentication establishes who the user is; authorization determines what the user is permitted to do.

A student session must not automatically grant access to administrative operations.

JSON responses

APIs commonly send structured JSON that JavaScript can parse.

PHP 
header("Content-Type: application/json");

echo json_encode([
    "success" => true,
    "message" => "Request completed."
]);
Foreign keys and database constraints

Foreign keys enforce relationships between records. Unique constraints prevent duplicate values where uniqueness is required. Appropriate indexes help queries locate records efficiently.

Frontend and backend validation
  • Frontend validation improves usability.
  • Backend validation protects the application and its data.
  • Database constraints provide an additional integrity layer.

All three can work together; frontend validation alone is insufficient.

11 • Data Integrity

11Important System Rules

Registrar requests

  • Allow only valid, active document types.
  • Reject duplicate document-type selections within the same submitted request.
  • Validate the allowed quantity for each item.
  • Calculate all fees on the server.
  • Store each selected document as an individual item.
  • Use one parent request and one associated queue ticket.
  • Prevent concurrent duplicate active requests according to the implemented business rule.

Accounting and payments

  • Do not trust payment amounts or charge IDs without validating them.
  • Ensure allocated charges belong to the correct student.
  • Prevent overpayment and invalid allocations.
  • Use transactions for related ledger and status changes.
  • Update Registrar item payment status only when its associated charge is actually covered by a verified payment.

Access and security

  • Verify the current session on protected endpoints.
  • Check roles and permissions on the server.
  • Use PDO prepared statements for user-supplied values.
  • Do not expose passwords, credentials, or private configuration in public notes.
  • Use safe error messages and keep detailed errors in server logs.
