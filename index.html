01 · INTRODUCTION

01 System Overview

What is QUEUESKI?

QUEUESKI is a student portal and queue-management system intended to organize student service requests, Accounting transactions, Registrar document requests, payment submissions, and office queue tickets.

Primary objectives

  • Organize student accounts and related information.
  • Manage Accounting and Registrar service queues.
  • Record charges and payments in an accounting ledger.
  • Allow students to request Registrar documents.
  • Support receipt submission and payment verification.
  • Track the processing status of tickets and requests.

Student

Uses student-facing pages and submits applicable service requests and payment information.

Administrator

Handles authorized administrative operations, queue actions, and payment reviews.

Accounting

Manages student charges, payments, and financial transaction records.

Registrar

Manages document requests, individual request items, and processing statuses.

Important distinction

The database shows how information is stored. The actual PHP and JavaScript determine which operations are available and how the system behaves when users interact with it.

03 · FEATURES

03 System Modules

Administrator Module

  • Provides administrative pages and operations.
  • Supports queue actions and counter assignments where implemented.
  • Uses backend endpoints to retrieve or update records.
  • Administrative actions must be protected by server-side authorization.

Student Module

  • Uses records from the students table.
  • Can use enrollment records from student_enrollments.
  • Provides access to permitted student-facing features.
  • Student sessions must not grant administrator privileges.

Accounting Module

  • Records charges and payments in accounting_transactions.
  • Uses payment_submissions to store submitted payment information.
  • Uses payment_bill_allocations to associate payments with charges.
  • Supports payment verification and rejection workflows.

Registrar Module

  • Loads available documents from document_types.
  • Stores a parent request in registrar_requests.
  • Stores selected documents in registrar_request_items.
  • Associates document charges with Accounting transactions.
  • Uses queue tickets to organize office processing.

Payment Receipt Module

  • Stores submitted payment details and transaction references.
  • Records the path of an uploaded receipt where applicable.
  • Tracks pending, verified, and rejected payment statuses.
  • Should restrict receipt access to authorized users.

Stores enrollment information by student, grade level, school year, term, section, strand, and enrollment date.

Serves as the ledger for charges and payments.

Stores the overall request submitted by a student.

  • requester_id — student who submitted the request.

  • request_type — request description.
  • quantity — parent-level quantity field.
  • purpose — reason for the request.
  • status — overall request status.
  • completed_at — completion timestamp, if set.

registrar_request_items

Stores each individual document included in a parent Registrar request.

  • request_id — parent request.
  • document_type_id — document catalog reference.
  • document_name — saved document name.
  • quantity — number of copies.
  • unit_fee — price per copy.
  • total_fee — item subtotal.
  • charge_transaction_id — related ledger charge.
  • status — item-specific processing state.

payment_submissions

Stores submitted payment details before and after administrative review.

  • student_id — submitting student.
  • payment_method — payment method.
  • amount — submitted payment amount.
  • transaction_reference — payment reference.
  • payment_datetime — date and time entered for payment.
  • receipt_path — saved receipt path.
  • status — pending, verified, or rejected.
  • reviewed_by and reviewed_at — review details.
  • ledger_transaction_id — related ledger payment, when present.

payment_bill_allocations

Connects one payment submission to a specific Accounting charge and records the amount allocated to that charge.

The unique constraint on payment_submission_id and bill_transaction_id prevents the same submission from having duplicate allocation rows for the same charge.

queue_tickets

  • office — Accounting or Registrar.
  • queue_number — ticket number.
  • request_id — optional linked Registrar request.
  • status — waiting, preparing, serving, completed, or cancelled.
  • started_at and completed_at — service timestamps.
  • skipped_at — timestamp for a skipped ticket.
  • assigned_admin_id — assigned administrator.
  • counter_number — assigned counter.
Why store fee snapshots?

Saving unit_fee and total_fee in each request item preserves the price used when that request was submitted, even if the catalog fee changes later.

06 · REGISTRAR

06 Registrar Request Workflow

How a multi-document request works

  1. The frontend loads active document types.
  2. The student selects one or more document types.
  3. The student chooses the quantity for each document.
  4. The interface calculates item subtotals and the displayed total.
  5. The student provides a purpose and submits the request.
  6. The PHP backend validates the submitted document IDs and quantities.
  7. The backend retrieves the current fees from the database and recalculates the total.
  8. One parent record is stored in registrar_requests.
  9. Each selected document is stored in registrar_request_items.
  10. Each document item can be associated with its own Accounting charge.
  11. A queue ticket can be associated with the parent request.
  12. Payment and processing statuses determine the next permitted action.

07 · ACCOUNTING

07 Payment Verification

Payment review process

  1. A student submits payment information and the required receipt, where applicable.
  2. The submission is saved in payment_submissions.
  3. The payment begins with a review status such as pending.
  4. An authorized administrator reviews the submission.
  5. The backend validates the payment details and transaction reference.
  6. The backend validates the charges selected for payment.
  7. Payment allocations are recorded in payment_bill_allocations.
  8. When the payment is verified, the ledger is updated as appropriate.
  9. The payment submission receives a verified status and review details.
  10. Related Registrar items can be updated when their charges are covered.

Important payment checks

  • Only authorized administrators can approve or reject submissions.
  • Allocated charges must belong to the correct student.
  • The amount allocated must not exceed the remaining balance of a charge.
  • The same payment submission must not be verified twice.
  • Payment methods and transaction references must be validated.
  • Related ledger and status changes should use a database transaction.
  • Receipt files should only be accessible to authorized users.

Payment-related statuses

Table Statuses or state
payment_submissions pending, verified, rejected
registrar_request_items awaiting_payment, payment_verified, processing, ready_for_release, completed, rejected, cancelled
accounting_transactions charge or payment transaction type
Payment and Registrar are connected

A Registrar document item should only be treated as paid when the corresponding charge is covered by a verified payment. A payment submission being verified does not automatically mean every outstanding bill for that student is paid.

08 · QUEUE OPERATIONS

08 Queue Management

Queue ticket information

The queue_tickets table stores information for Accounting and Registrar queues.

  • id — primary key.
  • student_id — associated student, if present.
  • request_id — associated Registrar request, if present.
  • office — accounting or registrar.
  • queue_number — queue number.
  • school_year and term — academic context.
  • status — current queue state.
  • started_at — time service started.
  • completed_at — time service completed.
  • skipped_at — time a ticket was skipped.
  • assigned_admin_id — assigned administrator.
  • counter_number — assigned service counter.
Database status Meaning
waiting Waiting to be served.
preparing Preparation is in progress.
serving Currently being served.
completed Service is completed.
cancelled Ticket has been cancelled.

Database constraints

  • (office, queue_number) is unique, so a number cannot be duplicated within the same office.
  • request_id has a unique constraint, so the same non-null request cannot be linked to multiple tickets.
  • assigned_admin_id can identify the administrator assigned to a ticket.
  • Foreign keys help preserve relationships between students, requests, and tickets.
Do not rely on the interface alone

Queue actions must be validated by the backend. The server should confirm the ticket's current status and the administrator's permissions before changing a ticket.

10 · TECHNICAL REFERENCE

10 Programming Concepts

Prepared statements

Prepared statements separate SQL commands from user-supplied values. They help prevent SQL injection when used correctly.

PHP · PDO 
$stmt = $pdo->prepare(
    "SELECT * FROM students WHERE Student_ID = ?"
);

$stmt->execute([$studentId]);

$student = $stmt->fetch(PDO::FETCH_ASSOC);
Database transactions

A transaction groups related database operations so that they can be committed together or rolled back if an operation fails.

PHP · PDO 
try {
    $pdo->beginTransaction();

    // Perform related database operations.

    $pdo->commit();
} catch (Throwable $e) {
    if ($pdo->inTransaction()) {
        $pdo->rollBack();
    }

    throw $e;
}
Sessions and authorization

PHP sessions maintain information associated with a logged-in user. Authentication identifies the user; authorization determines what the user is allowed to do.

A student session must not automatically grant administrative access.

JSON responses

PHP APIs commonly return JSON so JavaScript can read structured results.

PHP 
header("Content-Type: application/json");

echo json_encode([
    "success" => true,
    "message" => "Request completed."
]);
Foreign keys and unique constraints

Foreign keys enforce relationships between records. Unique constraints prevent duplicate values or combinations where uniqueness is required. Indexes can improve query performance.

Frontend and backend validation
  • Frontend validation helps users enter valid data.
  • Backend validation protects the application and its data.
  • Database constraints provide another layer of integrity.

Frontend validation alone is insufficient because users can bypass browser-side checks.

HTTP status codes
  • 200 — successful request.
  • 400 — invalid request data.
  • 401 — authentication required.
  • 403 — action not permitted.
  • 404 — resource not found.
  • 500 — unexpected server error.
11 · DATA INTEGRITY

11 Important System Rules

Registrar requests

  • Accept only valid document types.
  • Check that the selected document types are active.
  • Validate quantities on the server.
  • Recalculate all fees using the database catalog.
  • Save each selected document as an individual request item.
  • Use database transactions when creating related records.
  • Check the actual code's rules for duplicate active requests.

Accounting and payments

  • Validate payment amounts and charge IDs.
  • Ensure the allocated charges belong to the correct student.
  • Prevent duplicate payment processing.
  • Prevent overpayment beyond the remaining balance.
  • Use transactions for related ledger and status changes.
  • Only update a Registrar item when its associated charge is covered.

Queue management

  • Validate the current ticket status before changing it.
  • Confirm the administrator has permission to perform the action.
  • Prevent invalid status transitions.
  • Use the database constraints to preserve queue relationships.

Security

  • Verify sessions on protected endpoints.
  • Check roles and permissions on the server.
  • Use prepared statements for user-supplied SQL values.
  • Keep passwords stored as secure hashes.
  • Validate uploaded files and restrict receipt access.
  • Never expose private credentials in shared study materials.

13 · SELF-ASSESSMENT

13 Review Questions

System architecture

1. What is the role of HTML, CSS, JavaScript, PHP, and MySQL?

HTML structures the page, CSS styles it, JavaScript handles browser interactions, PHP processes server-side requests, and MySQL or MariaDB stores the data.

2. What happens when the frontend calls a PHP API?

The frontend sends a request. PHP validates the request, performs the required operation, accesses the database when necessary, and returns a response to the frontend.

3. Why should protected API endpoints check permissions?

Browser-side restrictions can be bypassed. The backend must verify that the current user is authorized to perform the requested action.

Database

4. What is the difference between a parent request and a request item?

registrar_requests stores the overall request. registrar_request_items stores the individual documents included in that request.

5. Why are foreign keys important?

They help maintain valid relationships between records and prevent references to nonexistent related records.

6. What is the purpose of payment_bill_allocations?

It records how much of a payment submission is allocated to a specific Accounting charge, allowing payments to be matched to the bills they cover.

7. Why does a request item store unit_fee and total_fee?

The fields preserve the fee applied when the item was created and record the subtotal for its requested quantity.

System workflows

8. Why must the backend recalculate Registrar fees?

Values submitted by a browser can be changed. The server must use trusted database fees to calculate the amount that should be charged.

9. Why should related database changes use a transaction?

A transaction helps prevent partial updates. If a required operation fails, the database changes can be rolled back.

10. Why is a verified payment not proof that every bill is paid?

A payment may cover only specific charges. The application must inspect the saved allocations and the remaining balance of each bill.

11. What is the purpose of queue ticket statuses?

They represent the current state of a ticket, such as waiting, preparing, serving, completed, or cancelled.

12. How would you trace a feature when debugging?

Start with the page, find its JavaScript event handler, identify the PHP endpoint, inspect the database query, and test the result and error handling.
